# hanzi-stroke-forge

为「我到底认识几个汉字」系列项目**生成缺失汉字的笔顺动画数据**的离线工具。

输入：权威笔顺数据（顺序 + 笔画类型）+ 开源中文字体。
输出：与 `hanzi-writer-data` 同格式的逐笔中心线数据，供小程序 / Android 端播放。

> 本仓库只做「数据生成」，不包含任何客户端代码。

---

## 1. 背景：为什么需要这个项目

小程序 `how-many-hanzi` 的笔顺数据来自
[Make Me a Hanzi](https://github.com/skishore/makemeahanzi)（经由
[`hanzi-writer-data@2.0.1`](https://www.npmjs.com/package/hanzi-writer-data)）：

- 字表：8105 字（《通用规范汉字表》）
- 数据源实际覆盖：**6866 字**（每字含逐笔 SVG 轮廓 + 中心线 medians）
- **1239 字没有字模**：都是生僻字 / 扩展区字（如 龘、靐、齉、䏝、㧐）

现状处理：缺字在详情页回退到楷体描字，工具页把它们从上传/校验中排除
（`miniprogram/lib/stroke-missing.js`）。Android 版做法相同。

本项目的目标：给这 1239 个字生成**可播放的近似笔顺动画数据**。

## 2. 数据来源

### 2.1 笔顺顺序与笔画类型（已有，全覆盖）

[takushun-wu/han-ideographs-stroke-order](https://github.com/takushun-wu/han-ideographs-stroke-order)
——**CC0 1.0**，29,167 条，依据以下国家标准整理：

- **GF 0023-2020《通用规范汉字笔顺规范》**（8105 字，2021-03-01 实施）
- **GF 3002-1999《GB 13000.1 字符集汉字笔顺规范》**（20,902 字）

文件 `order.tsv`，TSV，无表头：

```
序号	汉字	码位	笔画数	笔顺串
2	一	U+4E00	1	1
1990	测	U+6D4B	9	441253422
	    龘	U+9F98	48	414312511151511141431251115151114143125111515111
```

笔顺串含义：**1=横 2=竖 3=撇 4=点/捺 5=折**，一字符代表一笔。

已实测（2026-11）：**8105/8105 全覆盖，其中 1239 个缺字 1239/1239 全覆盖**，
笔画数与串长 0 不一致。

> 官方 PDF 仅供人工查阅，不要批量抓取；优先使用上述 CC0 数据库。

### 2.2 字形轮廓（需要字体）

候选字体（**许可必须逐一确认**，优先 OFL / 公共领域）：

| 字体 | 说明 |
|---|---|
| Noto Serif CJK SC / Source Han Serif | OFL，宋体风格，扩展区覆盖较好 |
| 花园明朝 HanaMin A/B | 扩展 B 覆盖好，许可需确认 |
| 其他覆盖扩展区的开源字体 | 需实测 |

**第一步必须先做字体覆盖率探测**：这 1239 字里有多少在该字体中存在字形。
字体没有字形，后续全部无法进行。

### 2.3 已有数据（可作对照）

- `hanzi-writer-data@2.0.1`：6866 字真实数据，来自 Arphic PL 楷体，Arphic Public License
- 生成数据的坐标系、字面率、观感应尽量与它对齐

## 3. 技术栈

| 用途 | 技术 | 备注 |
|---|---|---|
| 语言 | **Node.js + JavaScript**（ESM） | 与小程序仓库 `scripts/` 一致；不引入 TypeScript |
| 字体解析 | `opentype.js` | 读 TTF/OTF，取字形 SVG path |
| 栅格化 / 图像 | `sharp` | SVG→灰度图、缩放、合成，Windows 有预编译包 |
| 骨架化 | 纯 JS 实现 | Zhang-Suen 细化 + 图分析，不依赖第三方 CV 库 |
| GIF 预览 | `gifenc`（纯 JS） | 便于直接查看动画效果；也可输出 PNG 序列 |
| 浏览器预览 | HTML + Canvas | 复用小程序 `svgpath` 解析逻辑 |
| 可选质检 | 多模态大模型 API | **只做视觉打分**，不参与几何计算 |

**不使用 Python**：本机 Python 3.14 对部分图像库（scikit-image）兼容性不稳；
骨架化用纯 JS 足够，且能直接复用现有代码风格。

## 4. 流水线

```
order.tsv（笔数 N、类型序列）
        │
        ▼
字体字形 ──opentype.js──► SVG path（1024×1024，y 向上）
        │
        ▼
sharp 栅格化 512×512 ──► 二值图
        │
        ▼
Zhang-Suen 细化 ──► 骨架（1px）
        │
        ▼
骨架图分析：端点 / 交点 / 分支长度；剪枝毛刺
        │
        ▼
按「笔数 N + 类型序列」做约束切分（搜索/动态规划）
        │
        ▼
每笔点列平滑 ──► medians；沿骨架取距离变换值 ──► 笔画宽度 widths
        │
        ▼
输出 JSON（§5）+ 渲染 GIF（§6）
        │
        ▼
视觉质检（模型 + 人工抽检）──► 合并 / 重试 / 放弃
```

### 4.1 关键难点

1. **笔画切分**：骨架在笔画交叉处形成节点，需要用「总笔数 + 每笔类型」约束搜索
   最优分段，而不是简单沿分支切。
2. **方向先验**（用于给候选分段打分）：
   - 横：dx > 0，|dx| ≫ |dy|
   - 竖：dy 向下为主（注意坐标系 y 向上，视觉向下 = y 减小）
   - 撇：从右上到左下
   - 点/捺：向右下
   - 折：由两段构成（横折、竖折等），通常是一个节点连接两个方向
3. **复杂字**：齉（36 笔）、龘（48 笔）交叉极多，切分大概率不完美；
   这类字必须人工抽检，宁可放弃也不要输出错误笔顺。

### 4.2 大模型的定位（重要）

- ✅ 看渲染结果，指出「第几笔切错了 / 方向反了」
- ✅ 帮助编写、调试流水线代码
- ❌ 不生成坐标、不生成 SVG 路径

几何永远来自字体轮廓 + 细化算法；顺序永远来自权威数据。

## 5. 输出格式

### 5.1 坐标系（必须与现有一致）

`hanzi-writer-data` 使用 **1024×1024、y 轴向上**：

- 左上角 = `(0, 900)`
- 右下角 = `(1024, -124)`
- 小程序端换算：`screenY = (900 - y) * scale`

生成时需要把字体坐标（y 向下）翻转并缩放到该体系；字面率建议对齐
Make Me a Hanzi（字形包围盒约占 880×880，居中）。

### 5.2 JSON 结构

```json
{
  "v": 2,
  "medians": [
    [[120, 800], [300, 805], [480, 808]],
    [[300, 820], [305, 600], [308, 380]]
  ],
  "widths": [14, 12],
  "order": "441253422",
  "source": "forge"
}
```

- `v: 2`：与小程序云端数据版本校验一致（`data.v === 2` 才有效）
- `medians`：逐笔中心线点列（整数坐标），顺序即笔顺
- `widths`：逐笔平均笔宽（供变宽线条渲染）
- 可选 `strokes`：如果需要轮廓填充，可把 medians 按宽度偏移生成胶囊多边形；
  默认不生成（体积大、质量不稳定）

### 5.3 下游兼容性

小程序当前读取逻辑（`miniprogram/lib/strokes.js`）：

- `normalize()` 要求 `strokes` 数组非空且**可解析**
- `animateStroke()` 在缺少 medians 时退化为整笔填充

因此生成数据入库前，下游需要二选一：

- **方案 A（推荐）**：给生成数据加 `widths`，小程序支持「仅有 medians + widths」的绘制分支
- **方案 B（兼容）**：生成数据同时写出 `strokes`（用笔宽偏移出的多边形），
  这样不改小程序也能显示，但笔形较生硬、体积更大

## 6. 预览与验收

### 6.1 预览产物

- 单字 GIF（逐笔动画，200×200 或 300×300）
- 可选：`preview.html`，一次查看一批字

### 6.2 验收标准

| 项 | 标准 |
|---|---|
| 笔数 | 必须等于权威数据笔画数 |
| 每笔方向 | 符合笔画类型（横左→右、竖上→下、撇右上→左下…） |
| 覆盖 | 所有笔画拼起来能还原字形主体，无明显缺漏/重复 |
| 观感 | 人工抽检：简单字 ≥95% 可用，复杂字 ≥80% 可用 |
| 数据 | 坐标在合理范围（0..1024 / 900..-124），medians 无空数组 |

不达标的字**不输出**，继续走楷体兜底。

## 9. 风险与取舍

1. **质量天花板**：骨架近似 ≠ 真实笔形；复杂字可能永远达不到 6866 字的观感
2. **字体字形差异**：开源字体与《通用规范汉字表》标准字形可能有细微差异
3. **许可**：字体必须合规；生成数据若使用 OFL 字体，需确认衍生物的分发要求
4. **体积**：1239 字 × 约 2–3KB ≈ 3–4MB，只能放云存储/分包，不能进主包
5. **正确性**：教错笔顺的负面影响大于「没有动画」；因此宁可少生成、不硬凑

## 11. 下个会话从这里开始

建议第一步（M1）：

1. 初始化 `package.json`（`"type": "module"`），安装 `opentype.js`、`sharp`、`gifenc`
2. 写 `src/fetch-order.js`：下载并缓存 `order.tsv`，解析成 `Map<字, {count, order}>`
3. 写 `src/coverage.js`：接收一组候选字体，输出对 1239 字的覆盖统计
4. 选覆盖最高的字体，进入 M2 的 10 字 PoC
