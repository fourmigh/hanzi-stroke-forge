# hanzi-stroke-forge

为「我到底认识几个汉字」系列项目生成笔画动画数据的引擎。

核心目标：

```
generate(char) -> { v: 2, strokes, medians }
```

输入一个汉字，输出可直接播放的逐笔数据，效果像在米字格里描红写字。

引擎阶段只覆盖《通用规范汉字表》8105 字；成熟后再扩展。本仓库只做数据生成，不包含客户端代码，也不做界面、部署和小程序集成。

> 当前状态：M0 完成；M1 进行中（笔顺数据已验证，字体/KanjiVG 覆盖待探测）。

---

## 1. 下游现状

下游项目：`WeChatMiniProgram/how-many-hanzi`。

### 1.1 实际消费的数据格式

云端和缓存里的 JSON 是：

```json
{
  "v": 2,
  "strokes": ["M...Z", "M...Z"],
  "medians": [[[x, y], ...], ...]
}
```

- `strokes`：每笔一个 SVG path，构建时把空白替换成逗号压缩
- `medians`：每笔中心线，整数坐标
- `v: 2` 是下游的云端/缓存版本标记
- 下游 `normalize()` 只认 `strokes` 非空且可解析
- 下游**不读** `widths`、`type`、`order`、`source`

所以生成器只需要输出 `{ v: 2, strokes, medians }`，不要另起格式。

### 1.2 动画是怎么播放的

下游 `miniprogram/lib/strokes.js` 的 `animateStroke()`：

1. 沿 `medians` 逐帧画一条红色粗线
2. 线宽由「该笔轮廓面积 ÷ 中心线长度」估算
3. 画完后用真实 `strokes` 轮廓填充，盖住红线

这带来三个约束：

- **最终观感由 `strokes` 决定**，`medians` 只是书写轨迹
- `medians` 必须在轮廓内，否则红线会露到轮廓外
- 每笔 `medians` 至少 2 个点；少于 2 点会跳过动画、整笔直接填充

### 1.3 覆盖与缺字

| 项 | 数量 |
|---|---:|
| 字表 | 8105 |
| 已有数据 | 6866 |
| 缺字 | 1239 |

缺字构成（2026-11 实测）：

| 类别 | 数量 | 占比 |
|---|---:|---:|
| 基本区 U+4E00–9FFF | **967** | **78%** |
| 扩展 A U+3400–4DBF | 76 | 6% |
| 扩展 B U+20000+ | 196 | 16% |

**不是「都是扩展区字」**：绝大部分是基本区字，只是 Make Me a Hanzi 没有收录。

## 2. 数据源

### 2.1 笔顺（顺序 + 类型）

主候选：[takushun-wu/han-ideographs-stroke-order](https://github.com/takushun-wu/han-ideographs-stroke-order)，**CC0 1.0**。

- 29,167 条，依据 GF 0023-2020（8105 字）和 GF 3002-1999（20,902 字）
- `order.tsv`，TSV，无表头：`序号 汉字 码位 笔画数 笔顺串`
- 笔顺串：**1=横 2=竖 3=撇 4=点/捺 5=折**

**已实测（2026-11，`data/order.tsv`）**：

| 项 | 结果 |
|---|---|
| 非空行 | 29,167 |
| 单字条目 | 29,152 |
| 变体条目（汉字 + U+E0100–E0104） | 15 |
| 重复字 | 0 |
| 格式错误 / 非法笔顺字符 | 0 / 0 |
| 笔画数与串长不一致 | 0 |
| **8105 覆盖** | **8105 / 8105** |
| **1239 缺字覆盖** | **1239 / 1239** |

解析 `order.tsv` 时要注意：

- 15 行的「汉字」字段实际是「基础字 + 变体选择符」（如 `邦` + U+E0101），必须取第一个 code point：
  ```js
  const base = Array.from(field)[0];
  ```
- 与下游 `chars.data.strokes` 交叉比对（6,772 字）只有 1 个差异：**U+7699：order.tsv 13 画，下游 12 画**，M1 需人工核对。
- 建议再抽 20–30 字，与 cnchar 的笔画名称序列交叉校验，确认类型序列没有系统性偏差。

备用：`cnchar`（下游已在用）。

- 只能用于**已有 6866 字**的笔顺校验
- 对 1239 缺字只覆盖 **86 个**，不能作为缺字来源

下游 `STROKE_ORDER_FIXES` 已记录 10 个 hanzi-writer-data 错序字（肠、盖、苒、冉、谑、虐、陧、锺、鞲、聃）。生成数据应直接使用规范顺序，并复用这张表做交叉校验。

### 2.2 字形（本机实测，2026-11）

| 字体 | 覆盖 8105 | 覆盖 1239 缺字 | 缺什么 |
|---|---:|---:|---|
| Windows 楷体 `simkai` | 7906 | 1040 | 196 扩展 B + 3 基本区 |
| 宋体 `simsun` | 7909 | 1043 | 196 扩展 B |
| 微软雅黑 `msyh` | **8105** | **1239** | 无 |

结论：

- **1040/1239 有楷体字形**，可以走字体轮廓生成
- 196 个扩展 B 字只有黑体/宋体字形，观感会偏
- 系统字体只能用于本地 PoC，**不能随小程序分发，生成数据的再分发也有风险**

正式项目应使用开源字体：

| 字体 | 许可 | 用途 |
|---|---|---|
| 霞鹜文楷 LXGW WenKai | OFL | 主楷体候选 |
| 思源宋体 / Source Han Serif | OFL | 宋体回退 |
| HanaMin B / 花园明朝 | 需确认 | 扩展 B |
| BabelStone Han | 需确认 | 扩展 B |

M1 要用脚本实测每个候选字体对 8105 和 1239 缺字的「cmap 覆盖 + 非空轮廓覆盖」。

### 2.3 已有数据

- `hanzi-writer-data@2.0.1`：6866 字真实数据，来自 Make Me a Hanzi（Arphic Public License）
- `KanjiVG`：约 11,000 字，逐笔一个 path，CC BY-SA 3.0；日式笔顺，但几何可复用、可作对照

M1 也要统计 KanjiVG 对 1239 缺字的覆盖；能直接复用的字优先复用，不要重新生成。

## 3. 输出格式

### 3.1 坐标系与米字格

与 hanzi-writer 一致：

```
x ∈ [0, 1024]
y ∈ [-124, 900]
y 向上
```

米字格就是这个坐标系的中心正方形：

```
中心：      (512, 388)
边长：      1024
四角：      (0,900) (1024,900) (1024,-124) (0,-124)
水平中线：  y = 388
垂直中线：  x = 512
对角线：    (0,900)-(1024,-124)
            (0,-124)-(1024,900)
九宫格边界：x = 0, 341.3, 682.7, 1024
            y = -124, 216, 556, 900
```

所有字的字形都要归一化到这个米字格：

1. 取字形 bbox
2. 等比缩放到约 880×880
3. 平移到中心 `(512, 388)`
4. y 翻转：`y_out = 900 - y_font * scale`

这样不同字、不同字体的大小和位置一致，评测和模型判断才有统一基准。

### 3.2 JSON

```json
{
  "v": 2,
  "strokes": ["M 120 800 L 300 805 L 480 808 Z"],
  "medians": [[[120, 800], [300, 805], [480, 808]]]
}
```

约束：

| 项 | 要求 |
|---|---|
| 笔数 | 等于笔顺串长度 |
| `strokes` | 每笔一个可解析的 SVG path（`M/L/Q/C/Z`） |
| `medians` | 每笔至少 2 个点，整数坐标 |
| 数量 | `strokes.length === medians.length` |
| 压缩 | `strokes` 内空白替换成逗号 |
| 版本 | `v: 2` |

可选 `meta` 字段（字体、笔顺来源、置信度、算法版本）供调试使用，下游会忽略。

## 4. 生成方案

### 4.1 分层回退

不要一上来就跑骨架切分。按可靠性从高到低：

| 层 | 来源 | 覆盖 | 质量 |
|---|---|---|---|
| 1 | `hanzi-writer-data` | 6866 | 真实笔形，最好 |
| 2 | `KanjiVG` | ~11,000 | 真实笔形，日式 |
| 3 | 字体 + 笔顺 + 骨架切分 | 1040 缺字 | 近似，可接受 |
| 4 | 部件组合 | 扩展 B / 生僻字 | 真实部件，布局可能不完美 |
| 5 | 放弃 | 剩余 | 回退楷体 |

引擎阶段真正要「从字体生成」的是 1239 个缺字：

- 1040 个有楷体/宋体字形 → 第 3 层
- 196 个扩展 B → 第 4 层，或黑体字形 + 第 3 层
- 3 个基本区特殊字 → 单独处理

### 4.2 流水线

```
字体文件
  │ opentype.js
  ▼
整字轮廓（SVG path）
  │ 归一化到米字格
  ▼
1024×1024 二值 mask（复杂字用 2048）
  │ 欧氏距离变换（EDT）
  ▼
距离场 dist（半宽）
  │ Zhang-Suen 细化 + 剪枝
  ▼
1px 骨架
  │ 构建骨架图（端点 / 交点 / 边）
  ▼
笔顺串（笔数 N + 类型序列）
  │ 切分
  ▼
每笔中心线 medians
  │
  ▼
每笔轮廓 strokes
  │
  ▼
{ v: 2, strokes, medians }
```

### 4.3 切分（核心难点）

输入：骨架图 + 笔顺类型序列。

方向先验（注意 y 向上）：

| 类型 | 含义 | 方向 |
|---|---|---|
| 1 横 | 左→右 | `dx > 0`，`|dy|` 小 |
| 2 竖 | 上→下 | `dy < 0`，`|dx|` 小 |
| 3 撇 | 右上→左下 | `dx < 0, dy < 0` |
| 4 点/捺 | 左上→右下 | `dx > 0, dy < 0` |
| 5 折 | 多段 | 横+竖、竖+横、横+竖+钩等 |

做法：

1. 从端点/交点出发，沿边生成候选路径
2. 按方向、长度、米字格位置打分
3. 用贪心 + 回溯；复杂字用 beam search
4. 每笔标记已用边，最终覆盖所有骨架边

三个特殊情况：

- **环状骨架**（口、田、回）：骨架是闭环，没有端点，要先在环上找切点，再按笔顺分段
- **折笔**（类型 5）：一笔由 2–3 段组成，拐点必须落在骨架交点上
- **复杂字**（龘、齉）：搜索空间大，必须限制 beam 宽度并输出置信度

### 4.4 每笔轮廓

**方案 A：变宽轮廓（先做）**

- 沿中心线左右偏移 `dist`（半宽）
- 端点按类型加笔锋：横/竖圆头，撇/捺渐细成尖，折/钩加圆角
- 平滑后输出 SVG path
- 优点：不依赖精确切分，失败模式温和
- 缺点：笔形是合成的，不是真实字体轮廓

**方案 B：区域分配（后期可选）**

- 每个前景像素找最近骨架点，归属到该笔
- 每笔得到一个 mask
- marching squares 提轮廓 → 简化 → 平滑
- 优点：轮廓来自真实字形，拼合无缝
- 缺点：切分错误会直接体现在轮廓上

引擎阶段先用 A，保证「像写字」；某些字需要更真实时再对这批字走 B。

## 5. 米字格的作用

米字格不只是背景，它贯穿四个环节：

| 环节 | 用途 |
|---|---|
| 生成 | 字形归一化，统一大小和重心 |
| 切分 | 位置先验：横在左中→右中，竖在上中→下中 |
| 评测 | 每笔起止点、重心映射到 `[0,1]²`，跨字可比 |
| 大模型 | 诊断图上画米字格，提问有明确坐标 |

可以从 6866 个已有字统计「笔顺类型 → 起止区域」的位置先验，用于切分评分。

## 6. 大模型辅助

### 6.1 定位

大模型只做**位置裁判**，不生成几何：

| 能做 | 不能做 |
|---|---|
| 判断某笔位置是否合理 | 生成坐标 / SVG path |
| 在多个切分候选中选最优 | 替代骨架切分 |
| 指出哪一笔串到别的笔上 | 保证几何正确 |
| 给失败字排序 | 替代权威笔顺 |

笔数、顺序、类型永远来自权威笔顺数据；几何永远来自字体和算法。

### 6.2 推荐接口

OpenCode server 的：

```
POST /api/experimental/generate/decisions
```

特点：

- 支持图片（base64 + MIME）
- 支持结构化问题：`predicate` / `choice` / `score`
- 返回概率和置信度
- stateless，不走 agent 会话，适合批量

请求示例：

```json
{
  "model": { "providerID": "openai", "id": "gpt-4o" },
  "input": [
    {
      "type": "text",
      "text": "这是汉字「我」的笔画切分诊断图。米字格中心 (512,388)。笔顺：1撇 2横 3竖钩 4提 5斜钩 6撇 7点。"
    },
    { "type": "file", "mime": "image/png", "data": "<base64>", "name": "wo.png" }
  ],
  "questions": [
    {
      "type": "choice",
      "name": "overall",
      "instructions": "整体切分是否合理？",
      "choices": [
        { "value": "ok", "description": "每笔位置都合理" },
        { "value": "suspect", "description": "有 1-2 笔可疑" },
        { "value": "bad", "description": "明显错误" }
      ]
    }
  ]
}
```

前提：

- OpenCode server 在运行（`opencode serve --port 4096`）
- 模型支持图片输入（`GET /api/model` 的 `capabilities.input` 包含 `image`）
- 这是 experimental 接口，生产要锁版本或做降级

### 6.3 用法优先级

1. **候选排序**：生成 3–5 个切分候选，一次 `choice` 选最优。模型擅长相对比较。
2. **单笔质检**：只对几何置信度低的字，用 `predicate` 逐笔判断。
3. **位置先验**：只做九宫格级别的粗判断，不让模型给坐标。

### 6.4 可靠性校准

不能盲信模型判断。用 6866 已有数据做校准：

```
100 个正确样本（真实数据渲染）
100 个错误样本（故意打乱笔画 / 错位 / 串笔）
  → 让模型判断
  → 算准确率 / 召回率
```

如果模型分不清正确和错误，就只能当参考，不能进主流程。

对生僻字，模型可能不认识，只能判断「笔画是否连续、是否串笔、是否缺笔」，不能判断字义上的位置。

### 6.5 成本控制

| 场景 | 调用量 |
|---|---|
| 6866 已有数据 | 0 |
| 1239 缺字，几何置信度高 | 0 |
| 缺字，置信度中 | 1 次/字 |
| 缺字，置信度低 | 3–5 次/字 |
| 人工复核队列 | 模型先筛，人再看 |

## 7. 评测

### 7.1 用 6866 已有数据做 gold set

这是最客观的评测方式，不需要人工标注：

```
for ch in 6866:
    gold = hanzi-writer-data[ch]        // 真实 strokes + medians
    pred = generate(ch, font, order)    // 假装没有数据，重新生成
    score(ch) = compare(gold, pred)
```

指标：

| 指标 | 方法 | 权重 |
|---|---|---|
| 笔数 | `pred.strokes.length === gold.strokes.length` | 硬性 |
| 每笔方向 | 比较横/竖/撇/捺的起笔方向 | 高 |
| 中心线 | 每笔 medians 的 DTW / Hausdorff，归一化到 1024 | 高 |
| 拓扑 | 笔画交叉顺序、连接关系 | 中 |
| 轮廓 | 栅格化后 IoU | 低（字体不同，仅参考） |
| 置信度 | 引擎自评 vs 实际得分 | 校准 |

注意：gold 数据来自 Arphic 楷体，生成字体可能是 `simkai` / 霞鹜文楷。**字形不同，轮廓 IoU 天然偏低**，不能把 IoU 当主要指标。评测重点是笔数、方向、中心线、拓扑。

评测前先应用下游的 `STROKE_ORDER_FIXES`，否则 10 个错序字会误判。

### 7.2 抽样集

不要一上来跑 6866 全量。先分层抽约 240 字：

| 层 | 数量 | 例子 |
|---|---:|---|
| 简单独体 | 50 | 一、十、口、木、日、田 |
| 左右结构 | 50 | 我、你、好、测 |
| 上下结构 | 50 | 思、想、花 |
| 包围结构 | 30 | 国、回、园 |
| 多笔复杂 | 30 | 龘、齉、鬱、爨 |
| 折笔多 | 30 | 凹、凸、乃、及 |

### 7.3 最终验收

| 项 | 标准 |
|---|---|
| 笔数 | 100% 等于权威数据 |
| 方向 | 抽样集 ≥95% |
| 中心线 | DTW 中位数低于标定阈值 |
| 可播放 | 下游 `svgpath` 能解析，`normalize()` 通过 |
| 观感 | 盲测「像在写字」 |
| 置信度 | 每个字有分数，低置信度有标记 |

## 10. 风险与取舍

1. **复杂字切分**：龘（48 画）、齉（36 画）交叉极多，自动切分不可能 100% 正确；必须输出置信度，低置信度进人工复核。
2. **扩展 B 字形**：196 个字没有楷体/宋体字形，只有黑体；部件组合或开源扩展字体是备选。
3. **笔顺源覆盖**：takushun-wu 是否真的覆盖 8105，M1 必须实测；cnchar 只覆盖 86/1239，不能兜底。
4. **字体许可**：系统字体只能本地 PoC；正式项目必须用开源字体，并确认生成数据的再分发要求。
5. **大模型不可靠**：模型可能不认识生僻字，也可能误判；必须用 gold set 校准，只做辅助。
6. **质量天花板**：合成轮廓 ≠ 真实笔形；目标是「像写字」，不是「像素级复刻」。
7. **正确性优先**：教错笔顺的负面影响大于「没有动画」；低置信度字宁可标记、放弃，也不要硬凑。
